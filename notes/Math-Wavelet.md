# Math::Wavelet — design log

Why the module is shaped the way it is, and what running it on two engines
turned up. Kept outside `Math-Wavelet/` on purpose: none of it is
documentation a user of the module needs, and nothing here ships in the
distribution.

The module's own [README](../Math-Wavelet/README.md) says what it does. This
file says why.

## Why it exists alongside Math::Libgsl::Wavelet

The ecosystem has one wavelet module, `Math::Libgsl::Wavelet`, a binding to
GSL's wavelet transforms. It is the right choice where libgsl is installed and
what GSL offers is enough. That is less than it sounds:

| | `Math::Libgsl::Wavelet` | `Math::Wavelet` |
|---|---|---|
| needs | libgsl, NativeCall | nothing |
| wavelets | Daubechies 4–20, Haar, B-spline | the 106 of PyWavelets |
| signal length | a power of two | any |
| boundary | periodic | nine extension modes |
| multilevel | the full pyramid only | any level, coefficients per level |
| stationary, thresholding, denoising | — | yes |

So this is not a reimplementation of what is there: the overlap is the
periodic, power-of-two DWT, and the rest is new. A program that already
has GSL and needs only that overlap is better served by the binding.

## PyWavelets is the specification

Wavelet transforms have no standard. Normalisation, filter orientation, the
phase of the downsampling, the coefficient count at the boundary and the
meaning of each extension mode differ between MATLAB, GSL and PyWavelets.
Picking one and matching it exactly is worth more than picking the
"cleanest" convention, because then a result can be checked against a tool
people already trust, and a program can move between the two without its
numbers changing.

PyWavelets was the one to match. It is the most widely used of the three, its
extension modes are named and defined as MATLAB's are, and its source is
readable. Everything follows from
that:

- **The names are PyWavelets'**, kebab-cased: `wavedec`, `dwt-max-level`,
  `:trim-approx`, `:start-level`. Somebody porting a Python script should not
  have to look anything up.
- **The filter table is PyWavelets'**, generated by `tools/gen-table.py`.
  Daubechies coefficients can be computed by spectral factorisation, but
  doing that in Raku would give different last bits for the long filters. It
  would also make the high orders depend on the precision of a root finder.
  The table instead holds PyWavelets' doubles, and all 12 856 coefficients of
  the 106 wavelets parse back bit for bit on both engines.
- **Every expected value in `t/` is PyWavelets' output**, from
  `tools/gen-vectors.py`. None comes from this module, in the same way that
  Digest::Native's vectors come from `openssl`.

## The table is a string

87 KB of coefficients, written as Raku `Num` literals, would be compiled on
every precompilation and loaded on every `use`. The table is instead one
heredoc constant, with one tab-separated line per wavelet, which costs nothing
to compile. A wavelet's line is parsed the first time it is asked for, then
cached. A program that uses `db4` parses eight numbers.

An orthogonal wavelet stores only its decomposition lowpass filter. The other
three follow by reversal and alternating sign, which is exact, and the
generator asserts that the derived filters equal PyWavelets' own, bit for bit.
The same rule does **not** hold across the biorthogonal family: for
`bior2.x`, `bior4.4`, `bior5.5` and `bior6.8` the highpass signs come out the
other way. Rather than encode a second rule, the 30 biorthogonal wavelets
store all four filters.

## The transform is written as its definition

One level of analysis is `out[o] = Σ_j f[j]·x[2o + 1 − j]` over a signal
padded by `F − 1` samples of extension on each side. In periodization mode
the signal wraps instead of being padded, with PyWavelets' phase of `F/2`.
Synthesis is the adjoint of the same sum, taken with the reconstruction
filters. There are no special cases for short signals or long filters. Instead,
`extended()` answers for any index, however far outside the signal, so a
76-tap `db38` over a single sample is the same code path as `haar` over a
thousand.

That generality is what the vectors test hardest. Each of the 13 wavelets in
`dwt.vec` runs under every mode at lengths 1, 2, 5, 13 and 30. Those are
lengths at which the extension, for `db38` and `dmey`, wraps around the
signal several times.

The inner loops use native `num` arrays and C-style `loop`s. That is the one
concession to speed, and it is enough: a 4096-sample `db4` decomposition and
reconstruction takes about 0.1 s on either engine.

## What the two engines turned up

The library itself behaves identically on both engines: 2157 assertions on
each, with no `todo`.

- **Raku++ evaluates a call inside a WhateverCode once, when it builds the
  closure.** `(1, 1, 1).map(* + f())` is `(5 6 7)` on Rakudo and `(3 3 3)` on
  Raku++ 5.1.0: `f` ran once, at currying time. It surfaced in
  `examples/denoise.raku`, where `@clean.map(* + 0.3 * gaussian())` added the
  same noise sample to every point, which made the estimated σ zero. The
  example now uses a block, which reads better anyway. This is an engine bug,
  and the fix belongs in Raku++.
- **Neither engine will put an `Int` in a `num` array.** The first `idwt`
  bound its input to a `num` array directly, so coefficients given as
  integer literals died on both engines. Everything that enters a `num` array
  is now `.Num`-ed first, and `t/04-dwt2.t` passes integer bands to check it.
